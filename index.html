-- SYNTHETIC EXAMPLE · no internal tables or data WITH fab_ranked AS ( SELECT f.lot_id, f.wafer_id, f.eqp_id, f.chamber_id, f.product_id, f.step_id, f.route_id, f.recipe_id, f.process_time, ROW_NUMBER() OVER ( PARTITION BY f.lot_id, f.wafer_id, f.step_id ORDER BY f.process_time DESC, f.event_id DESC ) AS fab_rn FROM demo_fab_history AS f INNER JOIN demo_product_catalog AS p ON p.product_id = f.product_id INNER JOIN demo_step_catalog AS s ON s.step_id = f.step_id WHERE p.product_code = 'V9' AND s.process_group = 'MAIN' AND s.step_seq = '09' AND f.process_time >= CURRENT_DATE - INTERVAL '150 days' AND f.record_status = 'VALID' ), yield_ranked AS ( SELECT y.lot_id, y.wafer_id, y.test_time, y.good_die_count, y.total_die_count, ROW_NUMBER() OVER ( PARTITION BY y.lot_id, y.wafer_id ORDER BY y.test_time DESC, y.test_id DESC ) AS yield_rn FROM demo_yield_measurement AS y WHERE y.test_time >= CURRENT_DATE - INTERVAL '100 days' AND y.total_die_count > 0 AND y.test_status = 'COMPLETE' ), fab_latest AS ( SELECT * FROM fab_ranked WHERE fab_rn = 1 ), yield_latest AS ( SELECT * FROM yield_ranked WHERE yield_rn = 1 ), joined_data AS ( SELECT f.lot_id, f.wafer_id, eq.eqp_name, ch.chamber_name, rt.route_name, rc.recipe_name, f.process_time, y.test_time, 100.0 * y.good_die_count / NULLIF(y.total_die_count, 0) AS yield_pct, lm.lot_type, wm.wafer_size FROM fab_latest AS f INNER JOIN yield_latest AS y ON y.lot_id = f.lot_id AND y.wafer_id = f.wafer_id AND y.test_time >= f.process_time INNER JOIN demo_equipment_catalog AS eq ON eq.eqp_id = f.eqp_id LEFT JOIN demo_chamber_catalog AS ch ON ch.eqp_id = f.eqp_id AND ch.chamber_id = f.chamber_id LEFT JOIN demo_route_catalog AS rt ON rt.route_id = f.route_id LEFT JOIN demo_recipe_catalog AS rc ON rc.recipe_id = f.recipe_id INNER JOIN demo_lot_master AS lm ON lm.lot_id = f.lot_id INNER JOIN demo_wafer_master AS wm ON wm.lot_id = f.lot_id AND wm.wafer_id = f.wafer_id WHERE lm.lot_type = 'PRODUCTION' AND wm.wafer_status <> 'SCRAP' ) SELECT eqp_name, chamber_name, recipe_name, COUNT(*) AS wafer_count, ROUND(AVG(yield_pct), 4) AS mean_yield, ROUND(STDDEV_SAMP(yield_pct), 4) AS yield_std, MIN(test_time) AS first_test, MAX(test_time) AS last_test FROM joined_data GROUP BY eqp_name, chamber_name, recipe_name HAVING COUNT(*) >= 3 ORDER BY mean_yield, eqp_name, chamber_name;

발표자 · 1장

소개 · DataTalk

안녕하세요. V5P 소속 이유정입니다. 오늘은 Flash YE의 통합 데이터 분석 툴, 데이터톡을 소개드리겠습니다.

데이터톡은 현재 YE팀에서 구축 중인 전용 Postgre DB를 바탕으로, 자연어로 데이터를 조회하고 시각화와 분석까지 연결하는 프로젝트입니다.

소속과 이름을 소개하고, 자연어 조회·시각화·분석의 연결을 강조한 뒤 2장으로 이동합니다.

발표자 · 2장

도입 배경 · 전용 Postgre DB

저는 그동안 데이터레이크에서 주로 데이터를 추출해 왔습니다. 그런데 전사 공용 툴이다 보니, 조회가 몰리면 필요한 데이터를 제때 꺼내기 어려웠습니다.

해결 방법을 찾던 중 PA에서 사용 중인 Flake DB를 알게 되었습니다. 데이터를 많이 다루는 YE팀에도 이런 기반이 필요하다고 판단해, 제가 Postgre DB 도입을 제안했습니다.

이 제안은 실제 투자로 이어졌고, 현재 Flash YE 전용 Postgre DB가 구축 중입니다.

앞으로 메모리 생산량과 데이터가 늘어날수록 조회 부담도 커질 수 있습니다. 이번 전용 DB 구축은 기존 파일 시스템 기반 데이터레이크의 한계를 보완하고, 늘어나는 데이터를 안정적으로 활용할 기반을 마련하는 과정이라고 생각합니다.

조회 지연 경험 → 직접 도입 제안 → 실제 투자·구축 중인 전용 DB 순서로 설명합니다.

발표자 · 3장

활용성 개선 · 복잡한 SQL

DB 구축에서 한 단계 더 나아가, 이번 AX 프로젝트를 통해 제가 개선하고 싶은 것은 활용성입니다.

화면에 보이는 것은 데이터를 추출하기 위한 SQL 쿼리문입니다. 한두 번의 교육만으로 이런 복잡한 쿼리를 자유롭게 활용해 원하는 데이터를 정확히 추출하기는 쉽지 않습니다.

PA에서는 상황별로 SQL문을 정리해 두고, 사용자가 필요한 부분을 수정해서 데이터를 추출하고 있었습니다.

이 방식도 SQL에 대한 이해가 필요하다 보니, DB에서 할 수 있는 일이 많아도 실제 활용은 제한적이었습니다. 그래서 저는 엔지니어가 필요한 데이터를 더 쉽게 활용할 수 있도록 만들고 싶었습니다.

화면의 SQL을 짚고, 교육·템플릿 수정만으로는 활용에 한계가 있다는 점을 설명합니다.

발표자 · 4장

DataTalk의 방향 · 시연 안내

데이터톡의 핵심은 엔지니어가 평소 사용하는 언어로 필요한 데이터를 요청하고 추출하는 것입니다.

사용자가 필요한 데이터와 조건을 말하면, AI가 부족한 조건을 질문합니다. 대화를 통해 조건이 정해지면 그에 맞는 데이터를 추출하는 방식입니다.

여기에 시각화와 분석 기능을 더해, 간단한 작업은 데이터를 PC로 내려받지 않고도 앱 안에서 바로 확인하고 분석할 수 있는 통합 분석 툴로 발전시키고자 합니다.

이제 시연 화면을 보시겠습니다. 외부 AI를 활용해 제작한 시연으로, 사내 정보와 데이터는 설명용 가상값으로 대체했습니다.

자연어 요청 → 부족한 조건 확인 → 추출·분석의 흐름을 소개합니다. 가상값 시연임을 안내하고 5장으로 이동합니다.

AI 시연

AI 시연 · 자연어 요청부터 추출까지

화면 왼쪽에는 워크스페이스, 가운데에는 대화창, 오른쪽에는 데이터 결과가 있습니다. 입력창을 확대해 보겠습니다. “V9제품 MAIN STEP 09번 진행 설비별 수율 데이터를 조회해주고, 설비별 차이가 나는지 ANOVA로 분석해줘.” 이렇게 평소 사용하는 업무 언어로 요청합니다. 아직 조회 기간이 정해지지 않았기 때문에, DataTalk이 다시 확인합니다. “며칠치를 분석해드릴까요?” 이어서 답합니다. “FAB 150일, 수율 100일치를 조회해서 조인해줘.” 두 데이터의 기간을 서로 다르게 지정하는 것도 대화에 담을 수 있습니다. “네, FAB 150일치와 수율 100일치를 조회해 조인한 뒤, 설비별 수율을 ANOVA로 분석하겠습니다.” 기간에 답하면 사용자 입력은 여기까지입니다. 추가 실행 버튼을 누르지 않아도 요청한 조회와 조인을 이어서 진행합니다. 오른쪽 결과 영역을 보겠습니다. FAB 150일치 이력은 t1, 수율 100일치 데이터는 t2로 들어왔습니다. 이 예시에서는 각각 162행과 138행입니다. 이제 공통 키인 LOT_ID와 WAFER_ID를 기준으로 두 테이블을 결합합니다. 조인 결과는 t3, 120행입니다. 어떤 테이블에서 만들어졌는지 관계를 확인할 수 있고, 설비와 수율을 같은 결과에서 볼 수 있습니다. 이 숫자는 시연 데이터를 계산한 결과이며, 실제 데이터 규모나 처리 속도를 뜻하지 않습니다. 핵심은 최초 요청을 끝까지 기억하고, 조건이 갖춰지면 조회와 결합을 이어서 처리한다는 점입니다.

시안 5~8장. 전체 UI → 입력창 확대 → 질문 타이핑 → 기간 확인·답변 → 조회·조인 결과. 방향키로 이동합니다.

AI 시연

AI 시연 · 시각화·ANOVA로 확장

추출 다음에는 어떤 활용이 가능할까요? 시각화와 분석은 개발하면서 추가로 발굴한 가치이며, 현재 준비 중입니다. 처음 요청에 설비별 차이를 ANOVA로 분석해 달라는 목적이 이미 들어 있습니다. 따라서 같은 조회 결과로 그래프를 만들고, 설비를 비교 그룹으로, 수율을 측정값으로 자동 연결합니다. 사용자가 컬럼을 다시 고르거나 분석 실행을 누를 필요가 없습니다. 이번 가상 데이터는 설비별 40행씩, 모두 120행입니다. 분석을 마치면 그룹 간 평균 차이와 분포를 자동으로 보여줍니다. 이 예시에서는 그룹 평균 차이가 나타나지만, 이것만으로 설비가 차이의 원인이라고 말할 수는 없습니다. 그룹별 결과표와 해석도 이어서 준비합니다. 필요한 경우 결과만 저장할 수 있습니다. 큰 원시 파일을 PC에 계속 내려받는 과정을 줄일 수 있는 방향으로 준비하고 있습니다.

시안 9~12장. 요청의 분석 조건 자동 연결 → ANOVA 결과 → 분포 → 결과표. 12장에서 결과표를 보여준 뒤 전체 UI로 축소합니다.

AI 마무리 · 두 가지 활용 방식

기존처럼 데이터를 내려받아 Spotfire에서 분석하는 방식도 지원합니다. 여기에 앱에서 그래프와 분석을 확인하고, 필요한 결과만 저장하는 활용을 더하고 있습니다. 이제 발표자께서 확장 방향과 현업 활용 계획을 이어서 설명드리겠습니다.

분석 도구 확장 · API·MCP 연결

네, 지금까지 데이터톡에서 데이터를 조회하고 분석까지 이어가는 흐름을 보셨습니다.

데이터톡이 앞으로 더 확장해 나갈 영역은 분석 도구입니다. 방금 보신 ANOVA 분석 API처럼, 사용자가 필요한 분석 API를 직접 만들고 MCP로 연결해 앱 안에서 사용할 수 있는 구조를 구현하고 있습니다.

이러한 구조를 통해 현업의 요구에 맞춰 분석 기능을 추가하고, 활용 범위를 넓혀가고자 합니다.

분석 API → MCP → DataTalk 연결 구조를 설명합니다. 확장 구조는 구현 중인 방향입니다.

바로 활용할 수 있는 간편추출

실제 업무에 적용하기 위해서는 요청한 조건에 맞는 데이터가 정확하게 나오는 것이 중요합니다. 자연어 조회에서는 사용자가 필요한 데이터와 조건을 적절히 전달해야 하기 때문에, 요청 방식에 익숙해지는 데 어느 정도 적응 기간이 필요할 것으로 보입니다.

그동안에도 바로 데이터를 활용할 수 있도록, YMS와 비슷한 형식으로 조건을 선택해 추출할 수 있는 간편추출 도구도 추가했습니다.

자연어 조회와 간편추출 중 자신에게 편한 방법으로 필요한 데이터를 추출할 수 있도록 준비하고 있습니다.

정확한 조건 전달과 적응 기간을 설명한 뒤, 이미 추가한 간편추출로 연결합니다.
